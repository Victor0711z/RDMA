# 讲解清单（背这个就够用，不用逐行读代码）

这份清单是给"人"看的，不是代码注释。目标是：简历筛选 + 面试第一层追问都能应付。
每条都是"面试官可能怎么问 -> 你可以怎么答"的格式。

## 1. 这个项目是干什么的？

一句话：客户端把一个文件切成很多小分片，通过两条独立的网络路径（对应两张网卡）
并发发送给服务端，服务端按分片编号拼回原文件；如果某条路径中途故障，还没发完的
分片会自动改走另一条路径，不会传输失败。

## 2. 为什么要做"双网卡"，而不是一张网卡就够？

两个原因，都可以讲：
- **带宽聚合**：一张网卡的带宽是硬件上限，两张卡并行传能把总吞吐做高（类似
  RAID0 用多块盘叠带宽的思路）。
- **可用性**：单张网卡/单条链路故障时，传输不会整体失败，能自动切到另一条路径。

真实场景类比：GPU 训练服务器做分布式训练时，节点间用多张 RDMA 网卡做梯度同步是
业内常见做法（对应你投的这个岗位 JD 里"高性能网络"那条）。

## 3. 双网卡的负载均衡是怎么做的？为什么不是简单轮询（轮流各发一半）？

用的是"加权公平队列"(WFQ) 的思路：每条路径维护一个"虚拟进度" = 已分配字节数 /
权重，每次要发新分片时，永远挑虚拟进度最小、且还有可用发送窗口(credit)的那条路径。

好处：如果两张网卡带宽不一样（比如 25G 和 10G），可以给它们设不同权重
（比如 2.5:1），传输量会自动按这个比例分摊，而不是简单各发一半导致慢的那张
拖后腿。默认两条路径权重相等，就退化成"谁先空出窗口谁先发"，效果接近轮询但
更公平。

## 4. "credit / 滑动窗口"是什么，为什么需要它？

如果不限制，客户端会把所有分片一股脑全发出去，服务端/网络缓冲区会被打爆。
所以每条路径限定"最多同时有 N 个分片处于已发送但还没收到服务端确认(ACK)"的状态
（N 就是 window，配置里可调），发满了就先等对方 ACK 释放一个名额，再发下一个。
这是网络协议里最基础的流控思路（TCP 滑动窗口也是同样的道理）。

## 5. 故障转移具体是怎么触发、怎么处理的？

- 触发条件：某条路径的连接出错（比如对端断开、读写失败）
- 处理：把这条路径标记为"DOWN"，扫描"哪些分片是分配给这条路径、但还没收到
  ACK 的"，把它们重新塞回待发送队列，交给调度器分给还存活的路径重发
- 之所以能做到"不丢数据"，是因为分片有明确的"归属"记录
  （哪个分片当前分配在哪条路径上），故障时能精确知道要重发哪些，而不是
  "整个传输重来一遍"

## 6. 服务端为什么设计成"哑"的、不做任何调度？

调度、负载均衡、故障转移全部是客户端的事，服务端只做一件事：收到一个分片就
写到文件对应偏移，然后回一个 ACK。这样设计的好处是服务端逻辑简单、不需要
感知"这台客户端到底用了几条路径、怎么分配的"，換句話說調度策略可以在客户端
随便迭代升级，服务端完全不用跟着改。

## 7. TCP 版本和 RDMA 版本是什么关系？为什么要做两个？

两个版本共享同一套"分片调度 + 故障转移"算法代码（`scheduler.c`），只有最底层
"怎么把字节真正发出去"这一层不一样——这是用一个叫 `path.h` 的接口把"调度算法"
和"底层传输方式"解耦开了。

- TCP 版本：普通 socket，不需要任何特殊硬件，随便一台机器都能跑，用来验证
  算法逻辑本身是对的（分片有没有丢、乱、重复；故障转移触不触发）
- RDMA 版本：用 `libibverbs`/`rdma_cm`，真正做到网卡直接把数据 DMA 到对端内存，
  CPU 不用参与数据搬运（这是 RDMA 最核心的价值：零拷贝、内核旁路、低 CPU 开销）

如果面试官问"你怎么知道你的调度算法是对的，你有测试吗" —— TCP 版本 + 
`scripts/run_demo_tcp.sh` / `run_failover_demo.sh` 就是答案：脱离 RDMA 硬件也能
把正确性验证一遍。

## 8. RDMA 那部分具体是怎么传数据的？（这条是加分项里最容易被深挖的）

分两条线：
- **控制消息**（握手、ACK、"我发完了"这类小消息）：用标准的"双边"操作
  `SEND`/`RECV`，跟 socket 的 send/recv 心智模型差不多，接收方要提前 post 好
  接收 buffer。
- **分片数据本体**：用 `RDMA WRITE` + `immediate data`（单边操作）。发送方直接
  把数据写到接收方预先注册好、并且提前告诉了发送方地址(addr)和访问密钥(rkey)
  的那块内存里，接收方的 CPU **不参与这次数据搬运**（网卡硬件直接 DMA），
  接收方只是靠一个预先 post 的 RECV 拿到"有一片数据写到了第几号 slot、
  chunk_id 是多少"这个通知（这个通知信息塞在 32 位的 immediate data 里）。

如果被问"WRITE 和 SEND 有什么区别" —— SEND/RECV 是双边操作（两边都要有代码
参与），WRITE/READ 是单边操作（只有发起方的 CPU 参与，对端 CPU 完全不用管，
这正是 RDMA 相比传统 TCP 能做到低延迟低 CPU 开销的关键）。

## 9. 为什么 immediate data 只有 32 位，你是怎么解决"发的这片数据有多长"这个问题的？

约定 client 和 server 各自独立用同一个公式算：
`长度 = min(chunk_size, 文件总大小 - chunk_id * chunk_size)`。
两边输入一样（chunk_id、chunk_size、文件总大小握手时就同步过了），算出来的
结果必然一样，就不需要在 32 位 immediate 里再挤出字段来传输长度了。

## 10. 有没有踩过坑？（面试官很爱问这个，有真实故事分最高）

真实的一个：**测故障转移的时候，进程会被 SIGPIPE 直接杀死**。
原因是某条连接已经断开后，代码在清理阶段还是尝试往那个已经断开的 socket 上
写了一个"再见"消息，Linux 下默认往一个已经断开的连接写数据会触发 SIGPIPE
信号，默认处理方式是**直接杀掉整个进程**（不是返回错误码，是杀进程），
所以即使故障转移逻辑本身是对的，进程也会莫名其妙死掉。
修复方法是在进程启动时 `signal(SIGPIPE, SIG_IGN)`，忽略这个信号，让对应的
系统调用改成返回 `-1`（`errno=EPIPE`），走正常的错误处理分支（代码里本来就有
判断返回值的逻辑），而不是被信号杀死。这是网络编程里一个经典且容易忽略的坑。

## 11. 你怎么确定这份 RDMA 代码能在阿里云 eRDMA 上跑，不是随便写的？

因为代码用的是标准 `libibverbs` + `rdma_cm`，走 RC（Reliable Connection）
queue pair —— 这正是阿里云 eRDMA 官方文档确认原生支持的编程模型（标准的
`ib_write_bw` 等 perftest 工具都能直接在 eRDMA 上跑，不需要专有 SDK）。
可以顺便对比着讲：AWS 的 EFA 底层是 SRD queue pair，标准 verbs/`rdma_cm`
代码在 EFA 上跑不通，必须换用 libfabric —— 说明你在做技术选型的时候有考虑
过"不同云厂商的 RDMA 网卡编程模型不一定一样"这件事，不是拍脑袋写的。

## 12. 现在的局限性/还能怎么优化（如果被问"还有什么不足"，别说"没有"）

- 没做超时重传：只有"连接报错"才会触发故障转移，如果链路是"静默丢包/挂起
  但连接本身不报错"，目前检测不出来
- ACK 是一个分片一个 ACK，量大的时候有一定开销，可以优化成攒批确认
- 没有做加密/鉴权，明文传输，仅用于内网可信环境
- RDMA 版本的资源清理在极端错误路径下不是 100% 严谨（正常传输路径没问题）
