# 简历文案

两个版本，按你实际验证到的程度选一个用，不要用没跑过的数据。

## 版本 A：在真实 RDMA 双网卡环境（比如阿里云 eRDMA）上跑出过真实数据

- 基于 libibverbs / rdma_cm 实现双网卡 RDMA Write 零拷贝数据传输系统，设计加权
  公平调度算法按网卡带宽比例动态分配分片，双卡聚合吞吐较单卡传输提升 **XX%**
  （实测 XX Gbps -> XX Gbps）
- 实现基于 credit 的滑动窗口流控与故障自动转移机制：人为断开一条 RDMA 连接
  模拟网卡故障，验证传输任务无感知切换到存活链路，中断恢复时间 < **XX ms**，
  全程无数据丢失
- 抽象传输层接口解耦调度算法与底层网络实现，同时支持 RDMA Verbs 与 TCP 两种
  后端，便于在无 RDMA 硬件的环境中做单元测试与本地演示

XX 处必须是你在真机上跑出来的真实数字（跑法见 README「真机部署」一节），
不要填没测过的数字。

## 版本 B：还没有真实 RDMA 网卡，只跑过 TCP / 本地验证

- 设计并实现双网卡负载均衡与故障转移数据传输框架，核心调度算法（加权公平
  队列、故障转移重调度）与传输层解耦，可脱离硬件独立验证正确性
- 使用 libibverbs / rdma_cm 编写 RDMA 数据面（QP/CQ/MR 管理、RDMA Write +
  Immediate Data、credit-based 流控），实现 TCP 传输后端作为可独立运行的对照
  验证方案
- 实测双路径故障转移场景：人为切断一条连接，验证未完成分片自动转移到存活
  路径且文件完整性 100% 校验通过

版本 B 的关键是**不说"在 RDMA 网卡上测得 XX 提升"**，如实说验证方式是 TCP /
本地模拟。面试被追问时如实回答："RDMA verbs 部分是按标准范式实现的，受限于
没有真机，用 TCP 后端做了完整的正确性验证（分片调度、故障转移），性能数据
是在这个基础上测的"——这是诚实且站得住脚的工程限定，不丢分；反而如果编了没
测过的真机数据，一旦被问细节（怎么测的、瓶颈在哪、为什么不是 2 倍）会更被动。
